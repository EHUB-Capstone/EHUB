# Module 6 — Discovery API

`GET /api/showcase` requires authentication and returns `ApiResponse<PagedResponse<ShowcaseCardDto>>`.
Only non-deleted Published showcases with an existing project profile are discoverable.

| Query | Default | Rule |
| --- | --- | --- |
| search | omitted | Literal case-insensitive substring of the latest Project Name or Description; at most 100 characters |
| stage | omitted | Idea, Mvp, Beta, Launched; case-insensitive |
| industry | omitted | Exact normalized startup-industry name, at most 100 characters; matches ProjectTags of type StartupField |
| featured | omitted | true: faculty-selected Published showcases; false: non-featured Published showcases; omitted: all |
| semesterId | omitted | Non-empty GUID; semester of the latest Project |
| sort | newest | newest: PublishedAt descending; popular: LikeCount descending, then PublishedAt descending |
| page | 1 | Positive integer, at most int.MaxValue / 50 to prevent offset overflow |
| pageSize | 20 | Between 1 and 50 |

The latest project is selected by CreatedAt descending and Id descending before search or filtering.
Each lineage yields at most one card. All filters combine with AND. Final sorting uses showcase Id
as a stable tie-breaker. An unknown industry/semester or a page beyond the last page returns an empty list.

Card fields: id, projectName, description, logoUrl, developmentStage, publishedAt, teamName,
industries, likeCount, commentCount, isFeatured, featuredAt. Industries come from the latest Project's StartupField tags,
matching the existing Project Data representation. Review notes, review history and member data
are not part of this DTO.

Pagination follows the existing PagedResponse contract: items, pageIndex, pageSize, totalItems, totalPages.
The request parameter is `page`; the response field is `pageIndex`.

Example: `/api/showcase?search=garden&stage=Mvp&industry=AgriTech&sort=popular&page=1&pageSize=12`.

Invalid query values return 400; unauthenticated requests return 401. There is no class/role restriction
on discovery for authenticated users. Existing owner/moderation access rules remain on their own endpoints.

The existing status and published_at indexes are reused for Discovery. Featured adds the migration described below.
`GET /api/showcase/filter-options` also requires authentication and returns an ApiResponse with
industries (active catalog names) and semesters (id, code, name). Choices are independent of
showcase results: all active, non-deleted startup industries and all non-deleted semesters
(including planned and archived semesters) are returned, even when they have no Published showcase.
Student and Mentor can use these filters without staff-only APIs. Stage always offers all four stages.

The Gallery calls showcaseApi.list and getFilterOptions. Project cards open the existing detail page.
Search, filters, sort and paging run on the server. The Featured section and faculty-selection filter
use featured=true. Interaction counts remain read-only until Upvote is implemented.

## Faculty-selected Featured showcases

POST /api/showcase/{id}/feature and DELETE /api/showcase/{id}/feature require StaffOnly.
Both return ApiResponse<ShowcaseFeaturedDto> (id, isFeatured, featuredAt, rowVersion).
Admin may manage all showcases; Lecturer is scoped through ShowcaseAccess.ModeratableShowcases.
Student/Mentor receive 403, a foreign Lecturer receives 404, and an in-scope non-Published page returns 409.
Authentication is mandatory (401 otherwise). The operations are idempotent: repeating the same selection
does not change FeaturedAt, rowVersion or history. Expected concurrency conflicts return 409.

The flag and its history entry are saved atomically. Hiding a page through moderation or owner withdrawal
clears IsFeatured/FeaturedAt and records automatic removal in the same save. Restoring a page never
restores its old selection. Content edits do not grant owners the ability to change faculty selection.
Featured flags are included additively in detail, moderation and card DTOs; old fields/routes stay intact.

Migration: 20261105014241_AddShowcaseFeaturedSelection, generated by EF Core.
Up adds is_featured (boolean, not null, false by default) and featured_at (nullable timestamptz)
only to showcase_projects; no existing rows are selected automatically. Down drops only those two columns.
It does not remove Project, Team, Showcase or audit-history rows, but featured selections/timestamps are lost.

For an authorized local rollout, run from the repository root:

```powershell
dotnet ef database update --project backend/src/EHub.Infrastructure --startup-project backend/src/EHub.Api
```

Local rollback target (coordinate the code rollback as well, because new binaries require the columns):

```powershell
dotnet ef database update 20261104153303_AddProjectCompetitionEntries --project backend/src/EHub.Infrastructure --startup-project backend/src/EHub.Api
```

No migration is applied to the application's database by this task. Integration tests apply migrations
to their own disposable PostgreSQL database. Staging/production rollout is a separate operation.
